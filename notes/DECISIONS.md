# Architectural & Engineering Decisions (`DECISIONS.md`)

Every choice that another developer could reasonably make differently and that affects behavior, public API shape, numerical tolerances, array memory order, dependencies, or workflow is recorded here with its rationale and rejected alternatives.

Scope and the `v0.1.0` definition are in [`SCOPE.md`](SCOPE.md). Work is tracked in issue `#140`. This file holds decisions only.

## How to use this file

- **Numbers are permanent.** `DECISIONS #n` always refers to the same entry, wherever its text lives. The index below lists all of them.
- **This file holds only entries that are in force.** When a decision is superseded, the pull request that supersedes it moves the old entry, unchanged, to [`archive/DECISIONS-archive.md`](archive/DECISIONS-archive.md) and updates its row in the index.
- **Keep entries short.** An entry states the decision, why, and the alternatives rejected, in about 20 lines. Lists of files changed, test names and verification commands belong in the commit body and the pull request, not here. Anything that changes a tolerance or an expected value gives the old value, the new value and the source.
- **New entries are appended at the end** with the next number.

## DECISIONS #3: Physics Data Table Format (`.safetensors`), GitHub Releases Hosting, & Wave 3a/3b EOS Staging

- **Date**: 2026-11-04
- **Decision**:
  1. **Runtime Format (`.safetensors`)**: Convert MESA's ASCII and HDF5 physics data tables and pre-fitted spline coefficient arrays in Wave 0 into contiguous, 64-byte-aligned `float64` `.safetensors` files stored outside Git in `~/.cache/flexmesa/data/` (or `$FLEXMESA_DATA_DIR`). Both Rust (`safetensors` + `memmap2`) and Python/JAX (`safetensors.numpy`) memory-map (`mmap`) these files directly from the OS page cache with sub-millisecond startup latency and zero C-library dependencies.
  2. **Distribution & Hosting (`GitHub Release Assets` + SHA-256 Manifest + Local `$MESA_DIR` Builder)**: Keep the Git repository free of Git LFS binary blobs. Commit a lightweight `SHA-256` manifest (`src/flexmesa/data/manifest.toml`) and distribute modular `zstd`-compressed `.safetensors.zst` bundles via **GitHub Release Assets**, fetched automatically on first use or via `flexmesa data fetch`, alongside a local conversion command (`flexmesa data build --from-mesa $MESA_DIR`) for offline builds from an upstream MESA checkout.
  3. **Two-Subwave EOS Staging (`Wave 3a` $\to$ `Wave 3b`)**: Stage the 7-component EOS migration into **Wave 3a** (`Ideal + HELM + PC + Skye` + $C^2$ quintic smootherstep blending, requiring only the single `helm_table.safetensors` grid and 3rd-order forward automatic differentiation) followed by **Wave 3b** (`FreeEOS + OPAL/SCVH + CMS` 4D $(Z, X, \log T, \log Q)$ bicubic spline tensor evaluators).
- **Why**: MESA's 6 primary `.xz` table archives (`1.91 GiB` compressed) expand to `10.3 GiB` of ASCII text (`1.43 GiB` for `helm_table.dat` alone, which shrinks to `454 MB` in raw binary `float64`). Storing `2.18 GiB` in Git LFS would immediately exceed standard free LFS quotas, whereas GitHub Release Assets provide free storage and bandwidth up to `2.0 GiB` per file. Using `.safetensors` over HDF5 eliminates `libhdf5-dev` C linker and thread-mutex bottlenecks on the Rust track while enabling zero-copy shared OS page-cache `mmap` across parallel worker processes.
- **Alternatives Rejected**:
  - *Storing data tables in Git LFS*: Exceeds GitHub's free LFS quota on a single clone and forces every contributor and CI job to download `2.2 GiB` upfront.
  - *Using compressed HDF5 (`.h5`) as the primary runtime format*: Introduces native `libhdf5` C build/ABI dependencies and global API mutex locks in Rust, and prevents zero-copy OS `mmap` when chunk compression is enabled.
  - *Blocking all of `eos` on the 4D `FreeEOS`/`OPAL`/`CMS` tables*: Delays testing ionized stellar interior physics (`HELM + Skye`) that only need `helm_table`.

## DECISIONS #4: `LGPL-3.0-or-later` License & Portable Tooling Configuration

*(The licence part is superseded by `DECISIONS #63`; the portable-tooling part remains in force.)*

- **Date**: 2026-11-04
- **Decision**:
  1. **Repository License (`LGPL-3.0-or-later`)**: License `FlexMESA` under the **GNU Lesser General Public License v3.0 or later (`LGPL-3.0-or-later`)** matching MESA's root `LICENSE`, with explicit upstream attribution to the MESA Team and module authors.
  2. **Portable Project Configuration (`pyproject.toml` and `Cargo.toml`)**: Keep `pyproject.toml` and `Cargo.toml` free of machine-specific paths or local directory overrides so the repository builds and tests cleanly on any Linux, macOS, or Windows environment.
- **Why**: Adopting `LGPL-3.0-or-later` ensures full license compatibility with MESA's derived physics equations, test oracles, and converted data tables while permitting library linking by downstream users. Keeping build and test configuration files free of hardcoded local paths ensures reproducible builds across contributors and CI runners.
- **Alternatives Rejected**:
  - *Choosing a non-copyleft license (MIT/BSD/Apache-2.0)*: Incompatible with translating and redistributing `LGPL-3.0-or-later` and `GPL-3.0-or-later` algorithms and derived tables from MESA.
  - *Hardcoding local cache directories in `pyproject.toml` or `.cargo/config.toml`*: Leaks developer-specific filesystem assumptions into public configuration files instead of using standard environment variables (`RUFF_CACHE_DIR`, `MYPY_CACHE_DIR`, `CARGO_TARGET_DIR`) when needed locally.

## DECISIONS #9: Strict Test Tolerance Governance, Upstream Fortran MESA Bug Documentation & Multi-Line Git Commit Bodies

- **Date**: 2026-11-08
- **Decision**:
  1. **Zero Silent Test Tolerance Relaxation**: Never loosen an existing test tolerance to make a failing test pass. *(Updated 2026-11-16 by `DECISIONS #17`, `#145`, and `#166`)*: Upstream parity is judged strictly against real MESA `26.4.1` outputs (exact hexadecimal kernel outputs, upstream module `test_output` files, and stored real-MESA `history.data` trajectories in Rust `strict` mode) or exact mathematical/autodiff identities ($\le 10^{-10}$); Rust-versus-JAX agreement validates the derived JAX layer against Rust `strict` mode and is **never** evidence of upstream MESA parity.
  2. **Pre-Audit Discrepancy Notes (Updated 2026-11-17 by `#142`; Upstream Restoration Tracked in `#169`/`#178`)**:
     - **`eos/private/helm_electron_positron.dek` lines 566-567 (`dpepdda` and `dpepddz` missing $\rho$ factor)**: Upstream Fortran MESA computes the mixed density-composition derivatives of electron-positron pressure $\partial^2 P_{\mathrm{ele}}/\partial\rho\partial\bar{A}$ and $\partial^2 P_{\mathrm{ele}}/\partial\rho\partial\bar{Z}$ as `dpepdda = (zz*dindd + ww)*dindda` and `dpepddz = (zz*dindd + ww)*dinddz`, where `dindd = ye` ($\partial\text{din}/\partial\rho = Y_e$), `ww` $= \partial P_{\mathrm{ele}}/\partial\text{din}$, and `zz` $= \partial^2 P_{\mathrm{ele}}/\partial\text{din}^2$. By the product and chain rules on $\partial P_{\mathrm{ele}}/\partial\rho = \text{ww}(\text{din}, T) \cdot Y_e(\bar{A}, \bar{Z})$ with $\text{din} = Y_e \rho$, the exact derivative is $(\text{zz}\cdot\text{din} + \text{ww})\cdot\text{dindda}$, because $(\partial\text{din}/\partial\bar{A})\,Y_e = (\rho\,\text{dindda})\,Y_e = \text{din}\cdot\text{dindda}$. Upstream MESA's replacement of `din` ($= Y_e \rho$) with `dindd` ($= Y_e$) was dormant in Wave 3a.2 when `HelmTable::analytical_vertex` used a purely ideal Boltzmann vertex ($P_{\mathrm{ele}} \propto \text{din} \implies \text{zz} = 0$), and surfaced once the Chandrasekhar relativistic Fermi-Dirac cold term ($\text{zz} \neq 0$) was added in Wave 3a.5. Both Safe Rust and JAX analytical outputs preserve upstream MESA's `helm_electron_positron.dek:566-567` formula (`< 1e-13` internal cross-engine check across the 26 channels; `26.4.1` module-level vector promotion pending `#161`), while `tests/test_eos_wave3a2.py` checks `jax.jacfwd` consistency (note: channel tolerances in `test_eos_wave3a2.py` were broadened up to `< 2e-6` in pre-audit commit `47991c0`, audit tracking under `#161`).
     - **Native `@jax.jit` Skye vs. Safe Rust (`tests/test_eos_wave3a3.py`)**: In Wave 3a.3, `eval_skye_eos(..., backend="jax")` initially wrapped the Rust `PyO3` implementation via `jax.pure_callback` (comparing the Rust binary against itself at `< 1e-14`). In Wave 3a.5 (`97265a5`), it was replaced by a standalone `@jax.jit` XLA `float64` kernel (`_skye_jax.py`), whose FMA/Horner evaluation order agrees internally with Safe Rust to `< 1e-11` on `res` and `< 1e-8` / `< 2e-6` on 2nd/3rd-order free-energy derivatives (`d_dlnd`, `d_dln_t`). Per `DECISIONS #17` and `#23`, JAX-versus-Rust comparison validates only the derived JAX layer, not MESA `26.4.1`.
     - **Near-Center Pressure Scale Height Fallback (`star/private/hydro_vars.f90`, `tests/test_star_wave4_1.py` & `test_star_wave4_3.py`)**: In Wave 4.5 (`b684358`), aligning `scale_height` near $r \to 0$ with upstream MESA's $H_P = \min(P/(\rho g), \sqrt{P/(G\rho^2)})$ fallback causes $\partial H_P/\partial\ln r = 0$ inside the innermost 16 radiative core zones of the $1\,M_\odot$ ZAMS model (where $H_P = \sqrt{P/(G\rho^2)}$ is independent of $r$), so `test_star_wave4_1.py` evaluates $\partial H_P/\partial\ln r$ on interior zones `slice(nz - 128, nz - 112)` outside the central fallback sphere, and `test_star_wave4_3.py` detects both the convective core and convective envelope boundaries (`n_bdy >= 1`).
     - **`w5_riemann_rsp2` Composite Observable Profile Zero Crossing (`tests/test_wave5_bench.py`)**: *(Pre-audit benchmark diagnostic; provenance tracked in `#146`.)* In `w5_riemann_rsp2`, the per-zone benchmark digest `out_obs[k]` sums positive `(w / 1e5)` and negative `(de_t_dt / 1e8)` terms and crosses zero near $s_k \approx 0.435$. At $N_{\mathrm{zones}} = 8$, cell `k = 3` ($s_3 = 0.4375$) has $|v_3| / \max_j |v_j| = 1.4\times 10^{-3}$, and at $N_{\mathrm{zones}} = 128$, cell `k = 55` ($s_{55} = 0.4336$) has $|v_{55}| / \max_j |v_j| = 1.2\times 10^{-4}$, magnifying single-ULP CPU/XLA FMA differences between Safe Rust and `@jax.jit` to `2.06e-12` at $N_{\mathrm{zones}} = 8$ and `3.60e-11` at $N_{\mathrm{zones}} = 128$ when divided by $|v_k|$, whereas the norm-scaled relative error $\max_k |v^{\mathrm{Rust}}_k - v^{\mathrm{JAX}}_k| / \max_k |v^{\mathrm{Rust}}_k|$ and profile regression snapshots agree to $\le 1.45\times 10^{-15}$. `tests/test_wave5_bench.py` therefore bounds `rec.max_rel_err` at `< 5.0e-12` ($N=8$) and `< 5.0e-11` ($N=128$) for `w5_riemann_rsp2` alongside `< 1.0e-12` ($N=8$) and `< 1.0e-14` ($N=128$) for the remaining Wave 5 workloads.
  3. **Multi-Line Git Commit Body Requirement**: Every commit must carry a detailed multi-line commit body summarizing (a) the module-by-module changes, (b) the physical equations, upstream Fortran MESA files, or bug root causes, and (c) the verification tests and linters run.
- **Why**: Preserves scientific auditability across the git history and test suite so that any discrepancy between exact calculus (autodiff) and upstream Fortran MESA is explicitly isolated and documented rather than masked by a wider tolerance.
- **Alternatives Rejected**:
  - *Relaxing test tolerances across all channels when an upstream MESA discrepancy affects a subset of channels*: Masks potential regressions in the unaffected channels.
  - *Single-line commit messages*: Leaves the git log without context on why a change was made or how it was verified.

## DECISIONS #21: Packages Are Closed on Evidence by the Authoring Agent

- **Date**: 2026-11-16
- **Decision**: The authoring agent closes its own package issue when the pull request is merged and a closing comment links every acceptance criterion to its evidence: a CI run, a script-generated artifact committed in the repository, or a `file:line`. Criteria about agreement with MESA need a script-generated comparison against real MESA `26.4.1` output whose header records the MESA version string, compiler and SDK; the agent with the local MESA build runs it and commits the reference outputs and their recipe. Unmet criteria are named and moved to a specific open issue. The independent review audits closed packages afterwards and reopens any whose evidence does not hold. This replaces the "ready for verification" hand-off in `DECISIONS #17`.
- **Why**: Under the earlier rule the author could not close a package and the reviewing session often could not either, because it has neither the built Python extension nor the local MESA `26.4.1` build. Three packages (`#145`, `#163`, `#143`) were left open with nobody able to finish them. What the earlier rule was protecting against is completion by assertion; requiring linked, generated evidence keeps that protection without requiring a second party to be present.
- **Alternatives Rejected**:
  - *Keeping the reviewer as the only one who may close*: stalls every package on an environment the reviewer does not have.
  - *Letting the author close on its own report*: this is what produced the unsupported claims the audit found.

## DECISIONS #26: Diagnostic Harness Runs and Terminal-Output Controls (`Issue #147`)

- **Date**: 2026-11-17
- **Decision**:
  1. **Strict run first, diagnostic rerun second.** The history harness runs each case under strict control validation. If that run stops on unsupported upstream controls, the harness runs the case again with those controls ignored and reports the second run, labelled `diagnostic (N controls ignored)` in the `Run Mode` column of the case table.
  2. **A diagnostic run can never pass.** `evaluate_case_record` bars any run that ignored controls from the tolerance condition of every verdict, so it is a declared gap or an undeclared failure whatever its numbers are. This also applies when `--allow-unsupported-controls` is given to `flexmesa harness run` directly.
  3. **Terminal-output controls are accepted and recorded.** A key whose every upstream use at MESA `26.4.1` gates or formats a `write` to the terminal passes strict validation and is listed in `ControlValidationReport::terminal_output_keys` and in the generated controls report. - **Why**: After `#147` every one of the 106 cases stopped before step 1, so the case table could no longer show whether an engine change moved a trajectory, and the stops were dominated by keys such as `terminal_interval` (104 cases) that cannot affect a model. Keeping the diagnostic numbers restores the measurement without weakening the pass rule. Item 3 follows the precedent of `DECISIONS #25` for plotting keys.
- **Alternatives Rejected**:
  - *Report only the strict stop*: accurate, but gives no way to measure progress until every control of a case is ported.
  - *Give the harness the opt-out by default with ordinary verdicts*: a run with dropped controls could then be reported as a pass.

  - *Port MESA's terminal log now*: real work with no effect on any compared quantity; left to the output package.

## DECISIONS #27: Baseline Regression Check in the History Harness (`Issue #143`, `Issue #144`)

- **Date**: 2026-11-17
- **Decision**:
  1. **Every uncapped strict harness run is compared with the committed baseline run.** `flexmesa harness run` rebuilds the records of `benchmarks/history_harness/baseline_run_26_4_1.json` and reports a case as regressed when the baseline took steps and the run takes none, when the baseline reached upstream's termination condition and the run does not, or when the baseline history was within the manifest tolerances and the run is not. The list is written to `summary.regressions_vs_baseline`, and `--gate` fails on it.
  2. **Resource-limited and non-comparable runs are not judged.** A run that ended in a timeout or memory kill is inconclusive. Step-capped runs, fast-mode runs and runs given `--allow-unsupported-controls` directly are not compared.
  3. **The baseline is a regression snapshot, not a reference.** It records what `FlexMESA` did, right or wrong. Agreement with it is never evidence of agreement with MESA.
  4. **A change that makes a case worse on purpose updates the baseline in the same pull request.** `flexmesa harness run --cases <case> --update-baseline <file>` replaces only the executed cases; the pull request states which cases moved and why, with the before-and-after case table the rules already require.
- **Why**: While a case is a declared known gap its verdict cannot get worse, so with all 102 referenced cases declared the known-gaps gate could not see a case that used to evolve to upstream's termination and then stopped at step 0. Removing fabricated behaviour is expected to make cases worse; this check does not forbid that, it makes it visible and deliberate.
- **Alternatives Rejected**:
  - *Gate on any change in step count or deviation*: every legitimate trajectory change would fail the gate, which pushes authors toward not changing trajectories.
  - *Treat timeouts as regressions*: runner speed differs between machines, so the gate would fail for reasons unrelated to the code.
  - *Per-case expected outcomes in `known_gaps.toml`*: duplicates measured numbers in a hand-edited file, against `DECISIONS #26` item 4.

## DECISIONS #28: Storage of Subscripted Namelist Controls (`Issue #147`)

- **Date**: 2026-11-17
- **Decision**:
  1. **A Fortran subscript `i` is stored at Rust index `i - 1`.** `x_ctrl(i)`, `x_integer_ctrl(i)`, `x_logical_ctrl(i)` and `x_character_ctrl(i)` are read into `Vec` position `i - 1` (`crates/flexmesa-star/src/inlist_populate_limits.rs`). Code that ports upstream's `s% x_ctrl(n)` reads `x_ctrl[n - 1]`.
  2. **An unsubscripted assignment to an array control sets element 1.** This is what a Fortran namelist read does, so `required_termination_code_string = 'a'` and `required_termination_code_string(1) = 'a'` are the same.

- **Alternatives Rejected**:
  - *Keep index `i` with an unused element 0*: every array would carry a slot with no upstream meaning, and lengths would differ from upstream's by one.
  - *Reject unsubscripted assignment to arrays*: upstream's own inlists use it (`star/test_suite/pisn/inlist_convert:10`).

## DECISIONS #29: Derived JAX Contract, Full-Argument Auto-Dispatch, and Python Utility Disposition (`Issue #166`)

- **Date**: 2026-11-17
- **Decision**:
  1. **Derived JAX Role & Oracle Boundary**: Safe Rust `"strict"` mode is the canonical port validated against MESA `26.4.1`; JAX (`backend="jax"`) is a derived layer for automatic differentiation and batching validated against Rust `"strict"` mode and is never an upstream parity oracle (`DECISIONS #9`, `#17`). Cross-backend consistency tests execute the Rust side inside `numerics_mode_context("strict")` and are named as consistency checks rather than upstream or Fortran goldens.
  2. **Frozen Unverified Engine Helpers**: `flexmesa.star`, `flexmesa.binary`, and `flexmesa.astero` export `JAX_ENGINE_STATUS = "frozen-unverified-until-#143"` until the canonical Rust engine passes the `#143` history harness. End-to-end engine gradients will be exposed later via Implicit-Function-Theorem `@jax.custom_jvp` / `@jax.custom_vjp` rules reusing Rust Jacobians and `bcyclic`.
  3. **Full-Argument `backend="auto"` Dispatch**: `resolve_backend("auto", ...)` inspects all scalar, array, and nested `tuple`/`list`/`dict` numeric inputs so traced secondary arguments (`eta`, `log10_t`, composition fractions, boundary slices) never fall into Rust and raise `float(tracer)` errors.
  4. **Python Utility & Host-Builder Boundaries (`N1-27`)**: Keep `flexmesa.auto_diff` (JAX PyTree forward dual/hyperdual types for Python composition and `turb`), `flexmesa.num` (Python callable root/ODE helpers and `@jax.custom_vjp` `safe_root_jax`/`newton_solve_jax`), and host NumPy spline builders (`interp_1d.{pm,mp}`, `interp_2d.{bicub,bipm,akima,renka790}` when `backend="jax"`) as documented Python utilities rather than canonical engine implementations (`crates/flexmesa-{autodiff,num,mtx}`). Route traced `neu.neu_get` calls to `_jax.neu_get_jax` rather than the pure-Python `math` path.
- **Why**: Eliminates broken auto-dispatch on secondary traced arguments, removes false upstream parity claims from cross-backend tests and docs, freezes speculative JAX engine twins before Rust passes `#143`, and documents every package's true differentiation and device scope (`CPU + GPU/TPU` vs `CPU`-only Rust callbacks).
- **Alternatives Rejected**:
  - *Deleting `flexmesa.auto_diff` and `flexmesa.num` Python modules outright*: breaks `docs/api/numerics.md` public exports and Python callable-based ODE/root utilities (`jax.custom_vjp` `newton_solve_jax`) where crossing PyO3 on every residual call requires GIL callbacks.
  - *Re-implementing 1D/2D spline builders or `StarModel` in pure JAX before `#143`*: doubles engine porting work against an unverified Rust baseline.

## DECISIONS #43: Undefined Upstream Reads Become Loud Errors; Rust-versus-JAX Comparisons Are Tracked Expected Failures While JAX Is Frozen (`#169`, `#295`)

- **Date**: 2026-11-20 (rulings by the project lead)
- **Decision**:
  1. **Undefined upstream reads.** Where MESA `26.4.1` reads past the end of an array or reads a variable it has not set, there is no defined behaviour to reproduce. FlexMESA returns an explicit error on that path. This is the general rule and no longer needs a ruling per case. Each such path still gets a deferred issue under `#169` (upstream `file:line`, the inputs that reach it, and whether any shipped case does), a row in the `#169` register, and the issue number cited at the erroring line. The rule covers `#242`, `#271`, `#272`, `#287` and `#288`.
  2. **Scope of rule 1.** It applies only where the upstream result depends on memory contents. A defined upstream result that looks wrong is reproduced as before. Compiler-specific evaluation and anything else that cannot be reproduced exactly still goes to the project lead.
  3. **Rust-versus-JAX comparisons.** The JAX engine is frozen (`#166`) and is not being worked on. A test comparing Rust with JAX that fails because Rust was changed to follow MESA is marked `xfail(strict=True)` citing `#295` and declared in `benchmarks/history_harness/known_gaps.toml`, with its bound left at the value it had before the Rust change. The bound is not loosened and the measured value is not adjusted in the test. `#295` holds the register.
- **Why**: An undefined read returns whatever is in memory on the reference build, so any value FlexMESA chose would be an invented behaviour, and an error is the only choice that cannot be mistaken for agreement with MESA. For the JAX tests, loosening a bound or correcting the measured value hides the divergence; a strict expected failure records it and fails the gate when the comparison starts passing again.
- **Alternatives Rejected**:
  - *Substituting zero or the nearest valid element for an undefined read*: The run continues with a value upstream does not define.
  - *Reproducing what the reference build happens to read*: Depends on the compiler, the allocator and the run.
  - *Loosening Rust-versus-JAX bounds, or editing the frozen JAX code to follow each Rust change*: The first hides the difference; the second is the work `#166` defers.

## DECISIONS #46: Upstream `real(qp)` Is IEEE-754 `binary128` in Software (`flexmesa_math::Quad`), Not Double-Double

- **Date**: 2026-11-21
- **Decision**: Upstream `real(qp)` arithmetic is translated with `flexmesa_math::Quad`, a software IEEE-754 `binary128` type (113-bit significand, round to nearest with ties to even, gradual underflow). It provides the operations upstream applies to `real(qp)` values: `+`, `-`, `*`, `/`, integer powers in the multiplication order of `libgcc`'s `__powitf2`, `abs`, comparisons, and exact conversion from and correctly rounded conversion to `f64`. The type lives in `flexmesa-math` because `flexmesa-net`, `flexmesa-mtx` and `flexmesa-star` all need it and that crate is below all of them.
- **Why**: MESA `26.4.1` sets `qp = selected_real_kind(33, 4931)` (`const/public/const_def.f90`), which `gfortran` on `x86_64` implements as `binary128` through `libgcc`'s soft-float routines. The three double-double helpers now in the tree (`flexmesa-net/src/f64x2.rs`, and private types in `flexmesa-star/src/mesh_remap.rs` and `rsp_grid.rs`) carry about 106 bits with a different rounding rule, so they can give a different `f64` after the final conversion. The project lead ruled on 2026-11-20 that quad precision is reproduced rather than approximated.
- **Evidence**: 5,055 test vectors generated with exact rational arithmetic (`crates/flexmesa-math/tests/data/gen_binary128_vectors.py`) pass in `Quad`, and the same file agrees with GCC 13.3 `__float128` on `x86_64` (`check_binary128_vectors_gcc.c`). This checks the arithmetic, not any MESA result.
- **Limits**: This entry adds the type only. The existing double-double call sites are replaced one at a time in later pull requests, each with a harness comparison, because the replacement can change trajectories. Functions upstream never applies to `real(qp)` (`sqrt`, `exp`, `log`, ...) are not provided.
- **Alternatives Rejected**:
  - *Keep double-double*: not the arithmetic upstream runs.
  - *An external crate (`rug`, `f128`, `softfloat` bindings)*: adds C code or `unsafe`, against `#![forbid(unsafe_code)]`, for about 500 lines of integer arithmetic.
  - *Rust's native `f128`*: not available on the stable toolchain the workspace builds with.

## DECISIONS #50: The TDC Newton Solver Runs on a Translation of `auto_diff_real_tdc`; No Bracket Seed (`#321`)

- **Date**: 2026-11-21
- **Decision**:
  1. **Nested dual number**: `flexmesa_turb::tdc_dual::AutoDiffRealTdc<N>` holds a value, its derivative with respect to the Newton variable $Z$, `N` structure partials and `N` mixed partials, with each operation evaluating the formula of the upstream routine of the same name (`auto_diff/private/auto_diff_real_tdc_module.f90`). `bracket_plus_newton_search` iterates on it, so the returned $Y$ carries the partials of the last Newton update (`turb/private/tdc.f90:253-345`). The implicit-function-theorem step that replaced this before is removed.
  2. **No seed**: `TdcParams::y_face_guess` and the seeded bracket are removed. Upstream starts every search from `[-100, 100]`.
  3. **Real operands**: upstream has separate routines for a real operand (`mul_self_real`, `div_self_real`, and so on). The solver code is generic over the scalar type and promotes reals with `from_f64`, so it uses the two-dual routine. Values are the same; a partial can differ from upstream's in the last place.
- **Why**: MESA's Jacobian contains the partials its Newton iteration produces, which equal the implicit-function-theorem partials only at full convergence. The iteration may stop after one update from a bisection bracket of width one in $Z$, so the difference is not negligible, and it changes the solver path.
- **Limits**: Item 3 means the structure partials are not bit-identical to upstream's wherever a real operand is involved. (Follow-up in `#321`: `src/flexmesa/turb/{tdc,tdc_dual,tdc_search}.py`, `src/flexmesa/bench/tdc_fast.py`, and `crates/flexmesa-py/src/turb_py.rs` (`[f64; 12]`) now also follow the nested-dual / Newton-update scheme with no bracket seed, clearing `test_wave1_turb_tdc_stages_agree` from `known_gaps.toml`; `set_mlt` early returns and `set_tdc` unconditional Cox MLT / `get_TDC_solution` checks align with `turb/private/mlt.f90:53-181`, `turb/public/turb.f90:114-204`, and `#330`.)
- **Alternatives Rejected**:
  - *Keeping the implicit function theorem*: more accurate as a derivative, but not what MESA does.
  - *A non-generic copy of `compute_Q`, `eval_xis` and `eval_Af` using the real-operand routines*: would make the partials bit-faithful at the cost of two copies of the physics; left for when a hex reference for the partials exists.
- **Later measurement (`#339`)**: with `DualOrder1` following upstream's expressions (decision 52), all 1,024 partials in the MESA `26.4.1` `set_TDC` table match at 0 ULP, so the limit in item 3 was not observed in that table.

## DECISIONS #52: `DualOrder1<N>` Evaluates Upstream's Expression for Each Operation, in One of Two Forms Chosen by `N` (`#339`)

- **Date**: 2026-11-21
- **Decision**:
  1. **One expression per operation**: every method and operator of `flexmesa_autodiff::DualOrder1<N>` evaluates the expression of the upstream routine of the same name, in the same order, for the value and for the derivative. The generic rule `d1 = dx * f'(x)` is no longer used where it groups the factors differently.
  2. **Two forms**: upstream's generated modules come in two forms that round differently. `auto_diff_real_star_order1`, `auto_diff_real_15var_order1` and `auto_diff_real_1var_order1` write each derivative as one expression evaluated left to right (`3.0_dp*x%d1Array*pow2(x%val)`). `auto_diff_real_2var_order1` and `auto_diff_real_4var_order1` factor common terms first (`q0 = 3.0_dp*pow2(x%val)`, then `q0*x%d1val1`). `DualOrder1<N>` uses the factored form for `N == 2` and `N == 4` and the left-to-right form for every other `N`.
  3. **No added guards**: `safe_sqrt`, `safe_log` and `safe_log10` guard the value only, as upstream does. Their derivatives are `NaN` or infinite at `x == 0`.
  4. **Values that are products upstream**: `log10`, `safe_log10` and `log2` of a dual are `log(x)` times a reciprocal constant; `exp10` is `pow(10, x)`; `sinpi`, `cospi` and `tanpi` take `sin`, `cos` and `tan` of `pi*x`; `asinpi`, `acospi` and `atanpi` multiply by `powm1(pi)`; `dim` is `-0.5*y + 0.5*x + 0.5*Abs(x - y)`. `sgn` and `Heaviside` follow `auto_diff/private/support_functions.f90:48-68`.
- **Why**: the Jacobian the solver builds is made of these derivatives, and the Newton corrections follow from it. Against the MESA `26.4.1` hex table for `set_TDC`, 802 of 1,024 partials matched before this decision and all 1,024 match after it.
- **Limits**: the form is chosen from `N`, not from the upstream type each call site corresponds to. A Rust call site that uses `DualOrder1<2>` or `DualOrder1<4>` where upstream uses the star type (or the reverse) gets the other form; call sites were not audited. The second-order and third-order types still use the shared scalar kernels and were not compared with their upstream modules. Only the `set_TDC` table tests the left-to-right form against MESA output.
- **Alternatives Rejected**:
  - *A separate Rust type per upstream type*: exact by construction, but every generic kernel would need a second instantiation and the engine a wide rename.
  - *Keeping the generic chain rule*: simpler, and not what MESA computes.
  - *Keeping the guards on `safe_sqrt` and `safe_log`*: hides a `NaN` that MESA would produce at the same point.

## DECISIONS #53: Dashboard Coverage Runs Daily When `main` Has Changed, in Seven Instrumented Shards Built With the `ci` Profile (`#345`)

- **Date**: 2026-11-22
- **Decision**:
  1. **When**: `dashboard.yml` no longer measures coverage on pushes to `main`. A daily schedule runs a gate job that compares `main` with the commit recorded in `benchmarks/dashboard/coverage_commit.txt`, which `refresh-coverage` writes with the numbers it commits. Coverage runs only if `crates/`, `src/`, `tests/`, `scripts/ci/`, `scripts/dashboard/`, the Cargo files, `pyproject.toml`, the toolchain file or the workflow differ. A failed run leaves the commit unchanged, so the next day retries. Pull requests that touch the dashboard machinery and manual runs always measure. This applies to Rust and Python coverage alike.

  3. **One rayon thread under instrumentation**: the coverage shards set `RAYON_NUM_THREADS=1`. Coverage counters are memory shared by all threads, and worker threads running the same code contend for them: on one instrumented test binary four rayon threads took 682 s of CPU and 178 s wall, one thread 69 s and 55 s. Cargo still runs tests in parallel.

The per-test slowdown behind it is that thread contention; neither the code changes of that day nor the build profile changed the instrumented time of the same test locally. The coverage numbers inform the dashboard and gate nothing.
- **Limits**: line totals now come from LCOV records rather than from `cargo llvm-cov`'s own summary. On a test crate set the two agreed to 0.3 percentage points overall and about 2% per crate, so the dashboard's Rust figures move slightly once. Doctests are not measured, as before. The dashboard can show coverage up to a day older than `main`.
- **Alternatives Rejected**:
  - *Keep one job and raise its time limit*: hours per run, and runs queue faster than they finish.
  - *Merge raw profile data across shards*: needs every shard's instrumented binaries in one place; the per-line union gives the same answer for line coverage.
  - *A daily run whether or not `main` changed*: wastes a run on quiet days.

## DECISIONS #54: The Second- and Third-Order Dual Types Are Generated From Upstream's `auto_diff` Modules by a Script (`#349`)

- **Date**: 2026-11-22
- **Decision**:
  1. **Generated, not hand-written**: `crates/flexmesa-autodiff/src/order2_gen.rs` and `order3_gen.rs` are produced by `scripts/autodiff/translate_mesa_dual.py` from `auto_diff/private/auto_diff_real_2var_order2_module.f90` and `_order3_module.f90` at tag `26.4.1`. Each Rust function keeps the upstream routine's name, temporaries, their order and every parenthesis. The files are committed; regenerating needs a MESA checkout and is not part of the build.

The shared scalar kernels in `kernels.rs` and `kernels3.rs` remain for `apply_unary`, which takes caller-supplied derivatives and has no upstream counterpart.
- **Alternatives Rejected**:
  - *Translate by hand*: about 130 routines of up to 30 temporaries each.
  - *Generate at build time*: would make the build depend on a MESA checkout.

## DECISIONS #55: The Binary Step Loop Resets `rho = dm/dV` Before Remeshing, and Retries Restore the Reset Model (`#363`)

- **Date**: 2026-11-22
- **Decision**:
  1. **Where the reset runs**: `set_rho_to_dm_div_dv_for_new_step` (`star_utils.rs`, upstream `use_xh_to_set_rho_to_dm_div_dV`, `star/private/star_utils.f90:606-632`) runs where `prepare_for_new_step` calls it (`star/private/evolve.f90:1854-1857`): once per step, on the first try, after the `dt` checks and before the remesh. For a single star, `star_evolve_step` calls it before `remesh_star_before_step`. The binary step loop, which owns the per-step remesh of both stars, calls it for each star at the top of its once-per-step block, before remeshing. `star_evolve_step_part1` takes an explicit `prepare_new_step` argument and resets on the first try when it is true, independent of `do_remesh`. The binary loop passes `false` because it has already prepared the step.
  2. **What a retry restores**: upstream restores retries and redos from `xh_old`, which `new_generation` writes after the reset and the remesh (`evolve.f90:1895`, `set_current_to_old` at `evolve.f90:401`), or from `prev_mesh_xh`, stored right after the reset (`evolve.f90:1859-1872`), when `restore_mesh_on_retry` is set. The binary loop's `post_mesh_snap` therefore carries the reset density, and a new `pre_mesh_snap`, taken after the reset and before the remesh, replaces the pre-step snapshot as the `restore_mesh_on_retry` source. The pre-step snapshot remains the state restored when the step returns an error.
- **Why**: the binary loop took its retry snapshots before any step preparation. With the reset on the first try only, every retry started again from the unreset density. On the original RLOF fixture, model 1 then ended at 0.122 yr after 13 retries, where MESA ends at 125 yr after 3. With this order, the donor's `lnd lnT lnR L` at the first solver call match an instrumented MESA `26.4.1` run bit for bit in all 2402 zones, and model 1's counts match MESA's.
- **Limits**: a caller of `star_evolve_step_part1` that passes `prepare_new_step = false` without running the reset itself skips it. The binary loop is the only such caller. `pre_mesh_snap` is captured only when a star sets `restore_mesh_on_retry`, to avoid copying both stars every step.
- **Alternatives Rejected**:
  - *Run the reset on every attempt in `star_evolve_step_part1`*: it also gives MESA's model-1 counts, because the reset is idempotent on a restored model. But it runs after the binary loop's remesh, which changes the remeshed density on the first try, and it moves upstream's once-per-step call into the retry path.
  - *Recapture the pre-step snapshot after the reset*: the error path would then restore a model the caller never had.

## DECISIONS #58: Pull-Request Campaigns May Give Budget-Limited Cases a Short Budget; the Scheduled Campaign Runs in Shards (`#390`)

- **Date**: 2026-11-23
- **Decision**:
  1. **Short-budget tier**: `flexmesa harness run --short-budget-sec S` runs every case whose committed baseline row ended on the time budget (`run_status = "timeout"`) with `S` seconds and every other case with `--timeout-sec`. For those cases the gate compares the run as a prefix of the baseline row: it fails when the case takes no steps (baseline took some), ends other than on upstream's termination before the baseline's step count, or first leaves a track tolerance at an earlier model than the baseline (or inside the baseline's coordinate range when the baseline never left one). `--update-baseline` keeps the committed row when such a case ends on the short budget and replaces it when the case ends on a termination condition or an error. `--save-baseline` is refused with the short budget. Without the option nothing changes.
  2. **Shards**: `harness run --shard I/N` runs one of `N` disjoint parts of the selected cases. Cases whose baseline row ended on a time or memory budget are dealt round-robin first, then the rest, each in manifest order. `harness merge` rebuilds the records from the shard `--json-out` reports, writes one case table and one baseline candidate, and applies the gate once; it fails the gate when a shard or a selected case is missing or a case appears twice, and refuses shards run with different settings. `campaign.yml` runs the full harness as `harness_shards` (default 8) matrix jobs plus a merge job that keeps the job name `full-history-harness`, the artifact `campaign-history-harness-artifacts` and the `baseline_candidate.json` of `DECISIONS #51`. `workflow_dispatch` on a pull request's branch runs that branch's campaign; `harness_only` skips the other jobs and `short_budget_sec` selects the short tier (no candidate is then saved).
- **Why**: Strict mode is bit-identical across machines and thread counts, so a run of an unchanged engine reproduces a prefix of the baseline trajectory and only budget-limited outcomes depend on the machine. The cases that ended on the budget took about 65% of the last campaign's case time while showing nothing a prefix cannot show. Sharding turns one 355-minute job into parallel jobs of well under two hours.
- **Limits**: A short-budget run does not show what happens after `S` seconds: a change that breaks such a case later in its trajectory passes the short-tier gate and is found by the next full campaign. The zero-steps rule assumes `S` covers model initialization; a case whose setup takes longer than `S` would be reported. Per-shard timing on GitHub runners is still machine-dependent, so budget-limited rows in a sharded candidate move as they did before (`DECISIONS #51`).
- **Alternatives Rejected**:
  - *Comparing step counts or final values of short-budget runs*: they differ from a longer run by design.
  - *Writing short-budget rows into the baseline*: would replace a longer record of the same trajectory with a shorter one.
  - *Skipping budget-limited cases in pull-request campaigns*: loses the check that they still evolve and do not diverge earlier.
  - *Balancing shards by measured wall time*: the baseline normalizes wall times to zero for deterministic diffs, so there is no committed cost data.

## DECISIONS #59: A Run Cut Off by Its Budget Is Inconclusive and Is Checked as a Prefix of a Completed Baseline Row (`#447`)

- **Date**: 2026-11-23
- **Decision**: A case without a declared gap whose run ends on its time or memory budget (`timeout`, `oom_killed`) gets the verdict `inconclusive (<status>)`. It never counts as passing and is not an undeclared failure. When that case's committed baseline row completed (did not end on a budget), the baseline gate compares the run as a prefix of the row with the `DECISIONS #58` rules: it fails when the run takes no steps or first leaves a track tolerance at an earlier model (or inside the baseline's coordinate range). Rows whose baseline also ended on a budget are unchanged. `campaign.yml` also runs the `flexmesa-star` `--ignored` tests, so every declared Rust ignore is executed.
- **Why**: The first scheduled sharded campaign (`#447`) failed on `binary/evolve_both_stars` and `binary/jdot_ml_check`, which pass against MESA 26.4.1 and finish in about 490 s locally, but reached the 600 s budget on the GitHub runner. Their final columns were then compared on an incomplete run and labelled undeclared failures. Strict mode is bit-identical across machines, so only the budget outcome depends on runner speed (`DECISIONS #58`); the prefix check still catches a trajectory change within the steps that ran.
- **Limits**: A slower engine that pushes a passing case past its budget on every machine is reported only as inconclusive, not as a failure; the case table shows it and it never counts as passing. The prefix check needs the run's history to compare; a run killed before writing one is inconclusive unless it took no steps.
- **Alternatives Rejected**:
  - *A longer budget on GitHub runners*: the 600 s budget is global (Josh, 2026-11-23, `DECISIONS #57`).
  - *Declaring the two binary cases as known gaps*: they pass against MESA; a gap would be false.
  - *Ignoring budget-cut runs entirely*: loses the check that the part that ran still matches the baseline.

## DECISIONS #60: ADIPLS Elementary Functions Are Correctly Rounded in Strict Mode (`#171`)

- **Date**: 2026-11-23 (project lead)
- **Decision**: In strict mode the ADIPLS port evaluates `pow`, `exp`, `log` and the other elementary functions through `flexmesa-math` (correctly rounded, `DECISIONS #23`), like the rest of FlexMESA. Everything else follows upstream ADIPLS exactly: order of operations, the single-precision literals in double-precision expressions, and the common-block state.
- **Why**: MESA 26.4.1 compiles ADIPLS at `-O0` without CRMATH, so it calls the system libm directly. glibc on `x86_64` may select different implementations (for example FMA-built variants) at run time depending on the CPU, so upstream's ADIPLS output is not reproducible bit for bit across machines. Strict mode must be bit-identical across machines (Level 1), which a machine-dependent libm cannot give.
- **Limits**: Agreement with a given MESA build is expected at the 1-ULP level on `pow`-heavy paths (crlibm agrees with glibc on about 99.97% of `pow` arguments), not bit for bit; ADIPLS module goldens record this as a declared difference. A deferred issue under `#169` records the upstream non-determinism.
- **Alternatives Rejected**:
  - *Emulating the reference build's glibc variant*: ties strict mode to one glibc version and CPU dispatch path, and is a large port of its own.
  - *Platform libm in strict mode*: breaks cross-machine bit identity.
